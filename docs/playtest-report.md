## A. Bugs — 実際にプレイして見つけた問題

見つけた順に並べます。**すべて修正済みです。**
括弧内は「なぜ自動テストで捕まらなかったか」。

### 体験を壊していたもの

1. **掴み失敗が獲得に化けていた**（最も重い）
   アームから離れた瞬間の景品は空中にいるのに、「床を転がる距離」から
   初速を決めていた。空中では摩擦が効かないため、狙った 30px ではなく
   130px 以上飛んで出口に入っていた。端から端までのシミュレーションで
   1回目獲得率が 86.7%（設計値 23.6%）。難易度設計が根本から漏れていた。
   （解析的なテストは閾値の計算しか見ておらず、実際に won が出るかを
   見ていなかった。物理を回す端から端までのテストを足して発覚）

2. **出会いの演出で2匹が棚板から浮いていた**
   演出を別の SVG に重ねていたため、部屋の SVG とレイアウト箱が違い、
   viewBox の座標系がずれていた。演出の描画を部屋の SVG の中へ移した。
   （どちらの SVG も単体では正しく、結合したときだけ壊れる）

3. **演出と棚が同じぬいぐるみを二重に描いていた**
   クマの頭が二重に見えた。迎え役の選定を共有関数に切り出し、
   演出中は棚側が描画を止めるようにした。

4. **吹き出しがクマの顔を覆っていた**
   演出の一番見たい瞬間に、肝心の表情が隠れていた。
   ぬいぐるみの実際の高さを返す `plushTop()` を作って頭上へ逃がした。

5. **同種2匹を見分けられなかった**（仕様 5.4 の欠陥）
   個体差を色相回転だけで作っていたが、ミルクラビットの体色 `#efe6dc` は
   ほぼ無彩色で、色相を回しても何も変わらない。彩度と明度も
   個体差の軸に加えた。修正後はウサギ4匹が「4匹」に見える。
   （`applyIndividuality` は「元を変更しない」ことしかテストしておらず、
   「見た目が変わる」ことをテストしていなかった）

6. **アームが画面外にいた**
   `ARM_TOP` が擬似3D投影後に上端の外に出ており、何が起きているか
   分からなかった。

7. **奥行きの投影で右端の景品が画面外へ出ていた**
   盤面の世界幅を 236px に絞り、横ずれを z の中央基準にした。

8. **方向ボタンを押さずに決定を押すと何も起きなかった**
   説明なしで理解できる操作になっていなかった。入場した瞬間から
   狙う状態に入るようにした。

### 見た目・状態の問題

9. **棚の端の子がキャビネットの側板からはみ出していた**
   内寸 248px に半径 34px を4匹並べることはできない。
   総数 12 匹のまま 4段×3匹に組み替えた。

10. **瞬きの途中でアニメーションが止まると目が閉じたままになった**
    ドラッグを始めるとアンビエントが止まり、全員が目を閉じたまま固まった。

11. **シェア画像が余白だらけだった**
    縦長の部屋を正方形に収めると左右が大きく空く。縦 4:5 にして、
    壁と床を画像の端まで伸ばした。

12. **通算プレイ回数が「獲得数」を数えていた**
    仕様では「落とした回数」。ログを見て気づいた。

13. **クレーンの照準誤差を記録していなかった**
    仕様 7.6 の σ（照準のばらつき）を実測で較正するための数値を
    残しておらず、設計の仮定を検証できない状態だった。

### 併せて修正した堅牢性の問題

Codex による段階レビューで見つかったもののうち、体験に影響しうるもの:

- 最後の手段の直接配置が**別の景品を出口へ押し込みうる**
  （何も転がっていないのに別の子が落ちる。プレイヤーから見て理由が分からない）
- マルチタッチで2本目の指がドラッグを乗っ取れた
- `pointercancel`（ブラウザにジェスチャを奪われた）を成功として扱い、配置が確定していた
- 大きさの違う個体が隣り合うと重なった（間隔を片方の半径だけで決めていた）
- 購読者が例外を投げると以降の購読者に通知が届かなかった
- `movePlush` が段・座標・定員の不変条件を素通ししていた
- 保存に失敗しても成功として扱っていた（リロードで二重獲得しうる）
- 物理に速度上限がなく、極端な値で NaN が盤面に伝播しうる

## B. Friction — 遊びにくかった部分

1. **「これでいく」の意味が初回は一瞬わからない**
   横 → 奥の2段階だと理解できれば早いが、最初の1回は「何が決まるのか」が
   分からない。落下位置の目安リングは出しているが、
   横だけ決まったのか両方決まったのかが読み取りにくい。

2. **アームの下降〜上昇が体感で長い**
   下降 0.5 秒 + 上昇 1.1 秒 + 出口へ移動。見守りぬいぐるみの反応で
   かろうじて持っているが、反応がなければ確実に退屈になる長さ。

3. **獲得後、棚に戻るまでの 1.5 秒が長い**
   「やった！」を見せたい時間と、早く棚に戻りたい気持ちがぶつかる。

4. **棚の段の吸着が分かりにくい**
   ドラッグは段をまたげるが、どの段に載るのかが離すまで確定しない。
   ドラッグ中に載る先の段を示すものがない。

5. **最初は棚が広すぎる**
   4段 × 3匹の棚に1匹だけだと、空きが「まだ何もない」と読める。
   埋めるべき棚に見えると、目の前の子より空きスロットに目が行く。

## C. Emotion — 「かわいい」「嬉しい」と感じた瞬間

1. **落とした瞬間の「あっ！」がいちばん効く。**
   掴んだ景品が滑り落ちたとき、**自分は景品ではなくクマの方を見ていた。**
   仕様 17.2 の強い兆候 4「落とした瞬間、自分ではなく見守っている子の方を
   見たか」は、自分については **YES**。この一点だけで見守りぬいぐるみを
   作った価値があった。

2. **「もうちょっとかも。」で本当にもう一回やりたくなった。**
   失敗が「惜しい」に変換されている。取れなかったのに嫌な感じがしない。

3. **2匹が並んだ瞬間は確かに嬉しい。**
   ただし「嬉しい」の中身は、演出そのものより
   **クマが振り向いてくれたこと**だった。ウサギが落ちてくる動きより、
   先輩が「見た」ことの方が効いている。

4. **個体差を強めたあと、ウサギ4匹が「4匹」に見えた。**
   修正前は同じものが4つ並んでいるだけだったのが、
   大きさと色味が違うだけで「それぞれの子」になった。

5. **部屋にした瞬間、絵が変わった。**
   棚板を3本並べただけのときは収納棚の図に見えたが、
   キャビネットの枠・窓からの光・鉢植え・かご・ラグを置いたら
   「誰かの部屋」になった。ぬいぐるみは1匹も変えていない。

## D. Dead Moments — 退屈だった瞬間

1. **棚に戻ってから、次にやることがない。**
   置き直すか、またゲームセンターへ行くかの二択しかない。
   数秒眺めたあと手持ち無沙汰になる。

2. **アームが自動で動いている約2秒。**
   見守りの反応がなければ完全な待ち時間。

3. **2匹目以降の出会いが同じ。**
   短縮版にはしてあるが、起きることは毎回同じ。
   3匹目でスキップしたくなった（＝仕様 17.2 の**反証となる兆候**に当たる）。

4. **クレーンで何を狙うかの動機が弱い。**
   景品はランダムに並んでいるだけで、「この子が欲しい」という
   理由が盤面から生まれない。

## E. Hypotheses — 継続的に遊ばれるために不足しているもの

1. **翌日また来る理由がない。**
   日替わりの景品も、時間で変わるものも何もない。
   今日すべて遊びきったら、明日また開く理由が思いつかなかった。

2. **ぬいぐるみ同士の関係が「出会いの4秒」で終わっている。**（→ F-1 で対応済み）
   これが最大の欠落だと考える。このゲームの感情的報酬は
   「ぬいぐるみ同士の関係」だと定義したのに、実装されている関係は
   出会いの瞬間だけで、そのあと2匹は無関係に呼吸しているだけになっていた。
   隣を見る動きは入れていたが、12〜20秒に一度では気づかない。
   重要度が高いと判断したため、報告だけで終わらせず F-1 で実装しました。

3. **個体を「名指し」する手段がない。**
   `seed` で見た目は分かれたが、プレイヤーがその子を指して呼ぶ言葉がない。
   愛着は名前で固定されることが多い。

4. **棚が「飾る場所」ではなく「置く場所」になっている。**
   小物も家具もないので、配置の自由度が「左右にずらす」しかない。

5. **失敗の記憶が残らない。**
   「3回目でやっと取れた子」と「1回で取れた子」が棚の上で区別されない。
   苦労した子ほど愛着が湧くはずだが、その差が保存されていない。

## F. Next 3 Improvements — 次に実装するなら効果が高い改善

優先度順。いずれも仕様の「愛着が生まれるか」に直接効くものを選びました。

### 1. 棚での常時の相互作用 → **この場で実装した**

E-2 が MVP の中心的な欠落だと判断したため、報告だけで終わらせず
その場で実装しました。`useAmbientLife` に次を足しています。

- 隣（100px 以内）にいる子の方へ、ごくわずかに傾いて寄りかかる
- 隣が近いほど呼吸の位相が引き寄せられ、並んだ2匹が同じリズムで息をする
- 隣を見る間隔を 12〜20 秒から 5〜11 秒に詰めた（前者では気づかない）

実装後に見ると、クマとウサギが互いに少しもたれ合っていて、
「並んでいる」ではなく「一緒にいる」ように見えるようになりました。
出会いの4秒が終わったあとも関係が続きます。

**まだ足りないこと**: 片方をドラッグで離すと関係が消えるだけで、
「離された」ことへの反応がない。次はここです。

### 2. その子の「来た日」と「何回目で取れたか」を残す

**訂正**: 当初この項目に「獲得時の試行回数は既に保存している」と書きましたが、
これは誤りでした。`OwnedPlush` が持っているのは `acquiredAt`（日時）だけで、
**その子が何回目の試行で取れたかは保存していません。**
`attemptsOnBoard` は盤面ごとのカウンタで、獲得と同時に捨てられます。

したがってこの改善は、まず `OwnedPlush` に `wonOnAttempt` を足すところから
始まります。そのうえで、

- 今日来た子だけ、ほんの少し落ち着かない動き（`acquiredAt` で判定できる）
- 何回目で取れたかで、初回のリアクションを変える（フィールドの追加が要る）

を入れる。E-5（失敗の記憶が残らない）に効く。
「3回粘って連れて帰った子」が棚の上でそう見えるようになります。

### 3. 日替わりの1匹

盤面の主景品を日付から決める。ガチャにはしない。
「今日はこの子がいる」だけでよい。E-1（翌日来る理由がない）に効く。

`makeBoard` は既に乱数生成器を引数で受け取るので、
日付をシードにするだけで実装できる。

### （次点）名前をつける

E-3。`seed` で見た目は分かれたが、その子を指して呼ぶ言葉がない。
ただし依頼書 21 章の「肥大化させない」に触れる可能性があるため、
上の3つより後に置きます。

## 完成条件についての注記

自分で「○」を付けた項目のうち、正確を期すべきものを2つ挙げます。

### 条件6「4回以内に取れる」の保証の範囲

この保証は **「同じ子を狙い続けた場合」** に成立します。
不変条件は「その試行の対象」に対して働くため、毎回まったく別の景品を
狙えば、1匹あたりの前進はその分ゆっくりになります。

実プレイヤーは欲しい子を狙い続けるので実用上は問題ありませんが、
「どう遊んでも4回以内」ではありません。仕様 7.7 に明記してあります。
自動テストも同じ前提で書いています。

### 条件11「状態が保存される」の限界

localStorage が**読めない**場合（プライベートモード等）は初期状態で
起動し、プレイは成立します。破損データも初期化します。

一方 localStorage に**書けない**場合（容量超過、書き込み拒否）は、
プレイはメモリ上で続きますが**リロードで失われます**。
`store.isPersisted()` で検知はしていますが、現状その警告は
Developer Menu の中にしかなく、通常のプレイヤーには見えません。
→ この点は指摘を受けて、棚の画面に静かな一行を出すようにしました。

### 実プレイに基づく記述について

C・D 節と「実機で確認」の記述は、私が実際にブラウザで操作して
観察したものです。静的なコードからは検証できない主張であり、
その旨を明示しておきます。数値（テスト件数・ビルドサイズ・獲得率）は
コマンドの実行結果です。

## 既知の未解決事項

体験に影響しないため、今回は直していないもの。

- `react-dom/server` をブラウザ側で使っており、バンドルに
  サーバー描画コードが入っている（約 40KB）。`PlushSVG` を
  棚・クレーン・シェアで共有するための代償。手書きの文字列生成に
  置き換えれば削れるが、レンダラが二重になる方が危険と判断した。
- 厳しい CSP 下では `blob:` を `img-src` に許可しないとシェア画像が作れない。
  失敗しても画面は壊れず、エラー表示になる。
- 開発モードでは React StrictMode によりログが二重に記録される。
  本番ビルドでは起きない。

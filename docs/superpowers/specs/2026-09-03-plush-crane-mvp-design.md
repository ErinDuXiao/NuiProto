# ぬいぐるみクレーン + 棚 MVP 設計書

- 日付: 2026-09-03
- ステータス: 設計確定
- 依頼元: 「Webクレーンゲーム＋ぬいぐるみ棚 MVP 開発依頼書」

## 1. 目的

検証したい問いは一つ。

> **ぬいぐるみを獲得し、棚に持ち帰ったときに愛着が生まれるか。**

この設計書のあらゆる判断は「愛着が生まれるか」に従属する。クレーンの物理的リアリティ、
コンテンツ量、技術的高度さは、この問いに寄与しない限り価値を持たない。

プレイヤーに「この子を取った」ではなく「**この子を家に連れて帰った**」と感じさせる。

- クレーン = 入手方法
- 棚 = 生活する場所
- ぬいぐるみ同士の関係 = 感情的報酬

## 2. スコープ

### 作るもの

1. My Shelf 画面（自由配置・保存・環境アニメーション・シェア）
2. Crane Game 画面（擬似3D自作物理・見守りぬいぐるみ）
3. 出会いの演出（Priority 1）
4. シェア（PNG生成 → Web Share API → クリップボード）
5. プレイログ（JSON出力）
6. Developer Menu

### 作らないもの

依頼書 21 章の全項目（ユーザー登録、バックエンド、課金、広告、フレンド、チャット、
ランキング、PvP、**交換**、マーケット、トレード、NFT、大量の家具、大量のステージ、
本格ストーリー、ガチャ）。

加えて本 MVP では以下も作らない。

- リアルなアーム弾性・ワイヤー物理
- 複数ステージ／日替わり景品テーブル
- 家具・部屋の拡張
- i18n 機構（日本語固定。英語ワンポイントはリテラル）

| UI | React 18 |
| ビルド | Vite |
| 物理 | 自作簡易ソルバ（外部エンジンなし） |

| テスト | Vitest |

外部ランタイム依存は React / ReactDOM のみ。画像・音声アセットはゼロ。

### 3.1 なぜ自作物理か

Matter.js 等は「転がる・ぶつかる」は得意だが、本 MVP が必要とするのは
**「ちゃんと取れるが、少し転がる」という感情曲線の制御**である。
剛体ソルバの上でこれを実現するには拘束とチューニングに多大な時間を要し、
依頼書 27 章「クレーンの高度な物理表現に時間を使いすぎないでください」に反する。
球体のみを扱う 200 行程度のソルバなら、掴み・落下・出口誘導のパラメータを
直接数値で制御できる。

### 3.2 なぜ全画面 SVG か

ぬいぐるみ描画を単一コンポーネントに統一できる。結果として

- 棚での生活感（依頼書 13 章）と見守り演出（依頼書 8 章）が同一の部品で実装される
- シェア画像が、棚 DOM をスタンドアロン SVG に直列化して canvas に流すだけで生成でき、
  html2canvas 等の依存が不要になる
- 新種追加がデータ 1 オブジェクトで完結する（依頼書 23 章）

## 5. データモデル

### 5.1 Plush 定義（静的データ）

```ts
type Rarity = "common" | "rare" | "special";

type PlushDef = {
  id: string;              // "bear_01"
  name: string;            // "ブラウンベア"
  series: string;          // "forest_friends"
  rarity: Rarity;
  size: number;            // 描画・当たり判定の基準半径 26-34 (px)
  weight: number;          // 掴み保持のしにくさ 0.8-1.2（レンジ厳守。7.5 参照）
  softness: number;        // 変形量・掴まれやすさ 0-1
  art: PlushArt;           // 見た目パラメータ
};

type PlushArt = {
  body: string;            // 本体色
  accent: string;          // 耳内・腹などの色
  shape: "round" | "pear" | "long" | "blob";
  ears: "round" | "long" | "pointed" | "none";
  extras?: ("beak" | "tentacles" | "flipper" | "tail")[];
};
```

新種の追加はこのオブジェクトを 1 つ足すだけで完了する。IP コラボ時も
コード変更なしでデータとパラメータの追加のみで拡張できる。

### 5.2 収録ぬいぐるみ（10 種）

**Forest Friends**: Bear(common) / Rabbit(common) / Fox(rare) / Frog(common) / Deer(special)

**Ocean Friends**: Seal(common) / Octopus(rare) / Duck(common) / Jellyfish(rare) / Penguin(special)

初期所持は Bear。初回クレーンの主景品は Rabbit（size 大きめ・softness 高めで最も掴みやすい）。

### 5.3 永続スキーマ

```ts
type OwnedPlush = {
  uid: string;             // 個体 ID（獲得ごとに一意）
  defId: string;           // PlushDef.id
  acquiredAt: number;      // epoch ms
  x: number;               // 棚上の水平位置
  shelfRow: number;        // 0-2
  seed: number;            // 個体差シード（5.4 参照）
};

type CraneBoardSave = {
  prizes: { defId: string; x: number; z: number }[];  // 静止時のみ保存するため y=0
  attemptsOnBoard: number;                            // 7.4 参照
};

type SaveV1 = {
  version: 1;
  sessionCount: number;
  owned: OwnedPlush[];               // 配置は OwnedPlush が保持する
  craneBoard: CraneBoardSave | null; // 盤面の途中状態
  attempts: number;                  // 通算プレイ回数（リセットされない）
  pendingWelcome: string | null;     // 出会い演出が未再生の uid
  firstMeetingDone: boolean;         // フル版の出会い演出を再生済みか
  log: LogEvent[];                   // 上限 2000 件のリングバッファ
};
```

`version` 不一致・パース失敗時は初期状態にフォールバックし、破損データは破棄する。
サイレントに壊れた状態で起動しないこと。

**保存可能時点の限定**: `craneBoard` は速度・アーム位置・状態機械の途中状態を保存しない。
そのため書き込みは**クレーンが `idle` かつ全景品が静止しているときのみ**行う。
読み込み時は速度ゼロ・アーム原点・`idle` に正規化する。
試行の途中でリロードした場合、その試行は無かったことになり
`attemptsOnBoard` は最後に保存された値に戻る（プレイヤーに不利にならない方向）。

**獲得時の状態遷移の原子性**: 獲得は単一のストアアクション `winPlush(defId)` で行い、
盤面からの削除・`owned` への追加・`pendingWelcome` の設定・ログ記録を 1 回の更新にまとめる。
`pendingWelcome` は演出完了時にクリアする。演出中にリロードしても
`pendingWelcome` が残っているため演出は必ず 1 回だけ再生される。二重獲得は起きない。

### 5.4 個体差（愛着のための最小装置）

同種を 2 匹持ったとき「どっちも同じ」になると、個体への愛着が成立しない。
`seed`（獲得時に生成する 0-1 の乱数）から次を導出する。コストはほぼゼロ。

- 本体色の色相を ±6 度ずらす
- サイズを ±4% ずらす
- 呼吸周期・瞬き間隔・おしゃべりの頻度をずらす
- クリック時のセリフを個体ごとに固定の並びから選ぶ

名前の付与や個体ステータスは MVP では実装しない（依頼書 21 章の肥大化回避）。

## 6. ぬいぐるみ描画とポーズ

```ts
type Pose = {
  squash: number;    // 1.0 = 通常, <1 潰れ, >1 伸び
  tilt: number;      // 傾き (deg)
  eyeOpen: number;   // 0-1 (瞬き)
  lookAt: number;    // -1(左) .. 0(正面) .. 1(右)
  armRaise: number;  // 0-1 (万歳)
  hop: number;       // 縦オフセット (px)
};
```

`PlushSVG` は `PlushDef` と `Pose` のみを受け取る純粋関数コンポーネント。
状態を持たず、棚・見守り・クレーン盤面のすべてで同一のものを使う。

### 6.1 棚での生活感（依頼書 13 章）

`useAmbientLife` が以下を全個体に付与する。

- 呼吸: 2.4〜3.2 秒周期の微小な squash（個体ごとに位相をずらす）
- 瞬き: 3〜7 秒のランダム間隔で eyeOpen を 80ms 落とす
- 隣を見る: 12〜20 秒に一度、隣接個体が居れば lookAt をその方向へ 1.5 秒
- クリック: squash 0.85 → オーバーシュートで復帰、短いセリフを表示

静物にしないこと。棚を眺めているだけで何かが動いている状態を保つ。

## 7. クレーンゲーム

### 7.1 座標系と投影

景品は `{x, y, z}` を持つ球。y が高さ、z が奥行き。

```
screenX = originX + x + z * 0.35
screenY = originY - z * 0.55 - y
scale   = 1 - z * 0.0012        // 奥ほどわずかに小さく
```

描画順は z の降順（奥から手前へ）。

### 7.2 物理ソルバ (`physics.ts`)

球体のみを扱う。

- 重力 y 方向
- 床反発 0.35、床摩擦 0.86
- 球同士は水平方向の押し出し（位置補正 + 速度交換、反発 0.4）
- 壁クランプ
- 回転は水平速度から擬似的に導出（見た目用、物理には影響しない）
- 出口穴: 手前中央の矩形領域。中心が領域内かつ下向き速度なら落下 → 獲得

積分は固定タイムステップ 1/120 秒。累積時間からステップ数を求めるが、
タブ復帰時の処理雪崩を避けるため **1 フレームあたり最大 8 ステップで打ち切る**。

**物理と React の分離**: 物理ループは `useRef` 内の可変配列上で回り、
1 ステップごとに React の状態を更新しない。rAF ごとに 1 回だけ、
位置配列のスナップショットを `ArcadeScreen` の単一 `useState` に流す
（最大 60 回/秒、対象は SVG ノード 12 個程度）。
棚画面の呼吸・瞬きは CSS アニメーションと ref 経由の属性直接書き換えで行い、
**React の再レンダーを一切発生させない**。

### 7.3 操作（2 段階ボタン式）

```
待機 → [横移動: 長押しで左右] → 決定 →
       [奥移動: 長押しで前後] → 決定 →
       自動: 下降 → 掴む → 上昇 → 出口へ移動 → 開放
```

長押しで移動、離す or 決定ボタンで確定。移動中に画面端で自動反転はしない。
操作説明は画面上に常時 1 行だけ表示する（「長押しで移動、はなすと止まる」）。

### 7.4 試行カウンタの定義

`attemptsOnBoard` は現在の盤面での DROP 実行回数。**アーム下降開始時に +1** し、
結果（獲得・落下・空振り）に関わらず増える。現在の試行番号は
`n = attemptsOnBoard`（1 始まり）。

リセットされるのは次の場合のみ。

- 獲得成功して盤面が補充されたとき → 0
- Developer Menu の「景品再配置」→ 0

通算プレイ回数 `attempts` は別カウンタで、リセットされない（ログ用）。

### 7.5 掴みと落下

アーム接地時、最も近い景品との水平距離 `d`（x-z 平面上の距離）から保持力を決める。

```
k     = soft(s) / heft(w)                    // 個体係数
soft(s) = 0.75 + 0.25 * s                    // s∈[0,1]   → 0.75 .. 1.00
heft(w) = 0.85 + 0.30 * (w - 0.8) / 0.4      // w∈[0.8,1.2] → 0.85 .. 1.15
                                             // k ∈ [0.652, 1.176]（個体間 1.8 倍）

hold0    = clamp( (1 - d / R(n)) * k, 0, 1 )
hold(t)  = hold0 - drain(n) * (t / T_lift)   + 揺れ(見た目のみ、判定に影響しない)
```

- `T_lift` = 1.1 秒（下降完了から出口上空に到達するまで）
- `hold(t) < 0.15` に達した瞬間に開放 → 落下
- したがって**獲得条件は `hold0 >= 0.15 + drain(n)`**

`weight` のレンジを [0.8, 1.2]、`softness` を [0, 1] に固定する。
この制約により個体係数 k の幅は 1.8 倍に収まり、単一のアシスト表で
全個体の難易度曲線を設計できる。データ追加時もこのレンジを守ること。

揺れは Pose の tilt にのみ作用させ、`hold` の判定値には加算しない。
「揺れて落ちたように見えるが、実際は決定論的」であることが、
理不尽さを与えずに緊張感だけを出すための要点である。

### 7.6 アシスト設計（依頼書 7 章 成功率）

確率抽選は行わない。試行回数に応じて**掴み半径を広げ、保持減衰を弱める**。

| n | radiusAssist | R(n) | drainAssist | drain(n) | 必要 hold0 |
|---|---|---|---|---|---|
| 1 | 1.00 | 44px | 1.00 | 0.62 | 0.77 |
| 2 | 1.25 | 55px | 0.72 | 0.45 | 0.60 |
| 3 | 1.50 | 66px | 0.48 | 0.30 | 0.45 |
| 4+ | 1.75 | 77px | 0.29 | 0.18 | 0.33 |

`R0` = 44px、`D0drain` = 0.62。景品半径は 26〜34px。

許容照準誤差 `d <= R(n) * (1 - 必要hold0 / k)` は次のようになる。

| n | 最も掴みにくい個体 (k=0.652) | Rabbit (k=1.099) | 最も掴みやすい個体 (k=1.176) |
|---|---|---|---|
| 1 | 不可 | 13.2px | 15.2px |
| 2 | 4.4px | 25.0px | 27.0px |
| 3 | 20.5px | 38.9px | 40.7px |
| 4+ | 38.0px | 54.0px | 55.0px |

Rabbit は `softness` 0.9 / `weight` 0.85（k = 1.099）とし、初回盤面の主景品とする。

**照準誤差の想定分布**: x と z の誤差をそれぞれ `N(0, σ)` とすると、
`d` は尺度 σ のレイリー分布に従い `P(d <= D) = 1 - exp(-D² / 2σ²)`。
初見プレイヤーを σ=18px、慣れたプレイヤーを σ=9px と仮定する。
この σ は 2 段階ボタン式（停止タイミングで決まる）の実測値ではなく設計上の仮定であり、
実プレイ後にログの `d` 分布で較正し直す。

σ=18px（初見）での Rabbit 獲得率:

| n | 単発成功率 | 累積失敗率 |
|---|---|---|
| 1 | 0.236 | 0.764 |
| 2 | 0.618 | 0.292 |
| 3 | 0.903 | 0.028 |
| 4 | 0.989 | 0.0003 |

→ 1 回目 0.236（目標 0.15〜0.45 内）、4 回以内 0.9997。
σ=9px（上手い）では 1 回目 0.659 となり「上手ければ 1 回で取れる」を満たす。

### 7.7 盤面前進による構造的保証

上の確率は照準分布の仮定に依存する。仮定が外れても
「4 回以内に取れる」が崩れないよう、**確率に依存しない保証**を重ねる。

インパルスを与えるだけでは保証にならない。壁や他景品に阻まれれば距離は縮まず、
景品が既に出口上にいる場合は方向ベクトルが零になって保証が黙って壊れる。
そこで**不変条件として定義し、それを満たすまで機械が責任を持つ**設計にする。

#### 不変条件

DROP 時に**対象景品 T を 1 つ決める**（アーム位置に最も近い景品。掴めたかどうかに関わらない）。
そのときの出口距離を `before` とする。試行終了後、盤面が静止した時点で必ず次が成り立つ。

> **T が獲得済みで盤面から消えている、または `exitDistance(T) <= max(0, before - 30px)`**

この不変条件は、掴んで落とした場合（`released`）も、完全に空振りした場合（`nudged`）も
同じく適用される。**「何も起きない」試行は存在しない**（依頼書 6 章）。

#### 達成手順

1. 落下・空振り時、T に出口方向への水平インパルスを与える（見た目は「ころころ転がる」）
2. 盤面が静止したら不変条件を検査する
3. 満たしていなければ、不足分に応じた転がりを再度与える。**再試行は最大 3 回**
4. 3 回で満たせなければ、T を出口方向の直線上で
   `exitDistance = max(0, before - 30px)` となる点へ**直接配置する**。
   重なりは T ではなく**他の景品を押しのけて**解消する（保証済みの位置を壊さないため）
5. 目標位置が出口領域の内側になる場合（`before < 30px` のときなど）は、
   配置ではなく**獲得として扱う**

`before < 30px` の景品は目標距離が 0 となり、手順 5 により必ず獲得される。
距離が負にならない矛盾はここで解消される。

#### 帰結

初回盤面の主景品の出口距離 `D0` は 90〜140px に配置する。
不変条件により毎試行 30px 以上縮むので、

| 試行後 | 出口距離の上限 |
|---|---|
| 1 | 110px |
| 2 | 80px |
| 3 | 50px |
| 4 | 20px → 出口領域内 → 獲得 |

3 回失敗した時点で 60px 圏内（アームが触れるだけで転落する範囲）に入り、
**4 回目は掴みの成否に関わらず獲得できる。**
これは幾何的な保証であり、照準精度にも乱数にも物理の偶然にも依存しない。

#### 保証の範囲

不変条件は「**その試行の対象**」に対して成立する。毎回まったく別の景品を狙えば、
1 匹あたりの前進はその分ゆっくりになる。「4 回以内に取れる」は
**同じ子を狙い続けた場合の保証**である。実プレイヤーは欲しい子を狙い続けるので
これで足りるが、テストでもこの前提に沿って検証すること。

また、転がった景品が別の景品を突き落として獲得になることはある。
これは物理として正しく、体験としても嬉しい出来事なので禁止しない。
禁止するのは、最後の手段の直接配置が別の景品を出口へ押し込むこと。
何も転がっていないのに別の子が落ちるのは、プレイヤーから見て理由が分からない。

### 7.8 難易度の回帰テスト

Vitest で `craneMachine` を直接駆動して検証する。

1. σ=18px で 1000 試行 → 4 回以内獲得率 >= 0.95、1 回目獲得率 0.15〜0.45
2. σ=9px で 1000 試行 → 1 回目獲得率 >= 0.50
3. 全 10 種それぞれで n=4 の許容誤差 >= 35px（どの個体も 4 回目には取れる）
4. 落下 100 回すべてで、静止後の出口距離が 30px 以上縮んでいる
5. `D0` を 140px、照準を常に外す（d = 999）設定で 4 回 DROP → 必ず獲得

### 7.9 見守りぬいぐるみ（依頼書 8 章）

所持ぬいぐるみから 1 匹（既定では最初の 1 匹）を盤面手前に表示する。
状態機械で Pose とセリフを駆動する。

| 状態 | 表現 | セリフ例 |
|---|---|---|
| idle | ゆるい呼吸、アームを目で追う | 「あの子、気になる。」 |
| aiming | 目を大きく、身を乗り出す、左右に揺れる | 「そこ……！」 |
| dropping | 静止、瞬きを止める | （無言） |
| grabbed | 大きく跳ねる | 「きた！」 |
| missed | のけぞる、すぐ持ち直す | 「あっ！」 |
| nearExit | 前のめり | 「もうちょっとかも。」 |
| success | ジャンプ + 万歳 + 粒子 | 「やった！」 |

`missed` は 0.8 秒で idle に戻し、悲しみを引きずらせない。
クエスト化する台詞（「〇〇を取ってきて」）は入れない。

## 8. 出会いの演出（Priority 1）

獲得後、棚へ戻った直後に `MeetingCeremony` が操作をロックして再生する。
この演出は自由配置ロジックと混ぜず、独立したコンポーネントで管理する。

```
t=0.0  新入りが上から落ちて「ころん」と着地（squash 0.7 → 復帰）
t=0.6  先輩が新入りの方を向く（lookAt 補間）
t=1.0  先輩「はじめまして！」
t=1.8  新入りが 2 回跳ねる／粒子 3 つ
t=2.6  2 匹が並んで落ち着く
t=3.2  小さく "Welcome home."
t=4.0  演出終了 → 配置操作を解放、新入りに 2 秒だけ淡いリング
```

「GET!!!」のような強い演出、レアリティの誇張演出、金色、宝箱は使わない。
成功の温度感は "Welcome home." に揃える。

**反復への配慮**: 毎回 4 秒の強制演出は、繰り返すと待ち時間に変わる。

- 2 匹目（First Magic Moment）はフル 4.0 秒
- 3 匹目以降は短縮版 2.4 秒（先輩が向く → 「はじめまして！」 → 並ぶ）
- **いつでも画面タップでスキップできる**（スキップは即座に最終状態へ遷移する）
- 先輩役は新入りの最近傍 1 匹。同じ子が続けて選ばれた場合はセリフを変える

演出のスキップ有無はログに記録し、何匹目でスキップされ始めるかを観察する。

## 9. 棚の配置（依頼書 14 章）

- 3 段の棚板。各段の上面ラインに吸着（縦は自動、横は自由）
- ポインタイベント（マウス・タッチ共通）でドラッグ
- ドロップ時に重なりを検出し、水平方向へ押し出して解消
- 棚の外へは出せない。段をまたぐ移動は可能
- 配置は移動確定時に保存

**収容能力**: 棚の内寸幅は 320px（スマホ縦画面基準）、景品半径は最大 34px。
**1 段あたり 3 匹、4 段で最大 12 匹。**

当初は 3 段 × 4 匹としていたが、実プレイで端の子がキャビネットの側板から
はみ出した。キャビネットの内寸（248px）にぬいぐるみ 4 匹を重ならずに
並べることはできない。総数は同じ 12 匹のまま、段数と 1 段あたりの数を
入れ替えて解決した。収録は 10 種なので、全種を 1 匹ずつ集めても収まる。

スロットの座標定数（`SHELF_ROWS` / `PER_ROW` / `SLOT_X0` / `SLOT_SPACING`）は
`state/persist.ts` の 1 箇所に集約する。棚の描画と新しい子の配置が
別々の定数を持つと必ずずれる。

**過密時の規則**: 押し出しで段に収まらない場合、押し出された個体は
空きのある隣の段へ移す。全段が満杯の場合は移動を取り消して元の位置へ戻す
（無言で消えたり重なったりしない）。同種を複数所持して 12 匹を超えた場合、
超過分は棚に置かず「箱の中」として所持数にのみ計上する。MVP では
箱の中身を見る UI は作らない。

## 10. シェア（依頼書 17 章）

優先順に試行する。

1. 棚 SVG を直列化 → Blob → `<img>` → canvas → PNG（**1080x1350、縦 4:5**）

   当初は 1080x1080 の正方形としていたが、部屋が縦長（320:573）なので
   正方形に収めると左右に大きな余白が出て「見せたい絵」にならなかった。
   縦 4:5 にしたうえで、壁と床を画像の端まで伸ばして
   余白そのものを部屋の続きに見せる。
2. `navigator.share` が使え、ファイル共有に対応していれば Web Share API
3. 非対応時はクリップボードへコピー、それも不可ならダウンロード

画像に載せるのは棚・ぬいぐるみ・小さなゲーム名・所持数のみ。広告やロゴは載せない。

**直列化の制約**（ブラウザは SVG 画像内から外部リソースを読めないため厳守する）

- 色・寸法はすべて `style`/属性としてインライン化する。外部 CSS クラスに依存しない
- `<use>` / `<image>` / Web フォント / `filter` の外部参照を使わない
- **文字は SVG に含めず、SVG 合成後に canvas の 2D コンテキストで描画する**
  （フォント解決の差異を排除するため）
- 影は `feGaussianBlur` ではなく、半透明の楕円を敷いて表現する

`PlushSVG` はこの制約を満たす形で最初から書く。後から直すと全画面に波及する。

将来 `example.com/shelf/xxxxx` を実装できるよう、棚状態をシリアライズする関数
`encodeShelf(state): string` を切り出しておく。
MVP ではこの文字列を URL には使わないが、境界だけ先に作る。

## 15. テスト方針

Vitest で以下を回帰テストする。

1. **難易度**: 1000 試行シミュレーションで 4 回以内獲得率 >= 0.95
2. **盤面前進**: 掴み失敗時、景品と出口の距離が必ず縮む
3. **保存**: 保存 → 読込の往復で状態が一致する。破損データで初期化される
4. **配置**: ドロップ後に個体同士が重ならない。棚外に出ない

UI と感触は自動テストの対象外とし、実ブラウザでの実プレイで評価する（29 章）。

### 17.2 「愛着が生まれるか」の評価基準

これが本 MVP の中心仮説だが、ログだけでは測れない。実プレイでの観察項目を先に定義する。
自動テストの対象外であり、実装者が実ブラウザでプレイして自己申告で答える。

**強い兆候（これが出れば仮説は支持される）**

1. 2 匹目が並んだ瞬間に、配置を変えたくなったか
2. クレーンに戻る前に、棚を数秒眺めてしまったか
3. 同種 2 匹目を取ったとき「別の子」として扱ったか（`seed` の効果検証）
4. 落とした瞬間、自分ではなく見守っている子の方を見たか
5. スクリーンショットを撮りたいと思ったか

**弱い兆候（ログで観察する代理指標）**

- `shelf_dwell` の中央値が 8 秒を超える（一覧確認なら 2〜3 秒で済む）
- `plush_touched` が獲得数を上回る（用がないのに触っている）
- `plush_repositioned` が獲得数の 2 倍を超える（飾り直している）
- `welcome_played` の `skipped` が 5 匹目まで false（演出が待ち時間になっていない）

**反証となる兆候**

- 演出を 3 匹目でスキップし始める
- 棚に戻らず連続でクレーンを回す（コレクション動機が愛着を上回っている）
- `shelf_dwell` が 3 秒未満（一覧として消費されている）

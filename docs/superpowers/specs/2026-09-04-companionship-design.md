# 同居フェーズ 設計書 — ぬいぐるみたちが一緒に暮らしている

- 日付: 2026-09-04
- ステータス: 設計確定
- 依頼元: 「Webクレーンゲーム MVP 次フェーズ改善指示書」
- 前フェーズ: [2026-09-03-plush-crane-mvp-design.md](2026-09-03-plush-crane-mvp-design.md)

## 1. 目的

検証したい問いは一つ。

> **プレイヤーは「ぬいぐるみを所有している」ことより、
> 「ぬいぐるみたちが一緒に暮らしている」と感じたときに、より強い愛着を持つか。**

前フェーズの実プレイで、最も強かった感情的瞬間は次の2つだった。

- 景品を落とした瞬間、プレイヤーは**景品ではなく見守りぬいぐるみを見た**
- 2匹が並ぶ嬉しさの中身は「並んだこと」ではなく、**先輩が振り向いて見たこと**だった

どちらも「モノが増えた」ではなく「関係が生まれた」ことによる。
このフェーズは、その関係を**獲得の瞬間だけでなく棚に戻ったあとも持続させる**。

### なぜ Daily を入れないか

日替わり景品・ログインボーナス・広告・課金・SNS は今回**実装しない**（依頼書20章）。

外的報酬を先に入れると、プレイヤーが戻ってきた理由が
「ぬいぐるみに会いに来た」のか「新しい景品を見に来た」のか分離できなくなる。
**新しい景品がなくても棚を見たくなるか**を先に確かめる。

## 2. スコープ

### 作るもの

1. ぬいぐるみを「種類」ではなく「個体」として扱うデータモデル（v2 移行）
2. 個体ごとの来歴（いつ・何回目で・誰が見ていたか）とプロフィール表示
3. 棚での隣接関係と、そこから生まれる持続的な相互作用
4. 並べ替えの操作性改善
5. クレーンの Reaction Director（物理イベント → 感情反応）
6. 吹き出しの配置保証
7. プレイログの追加と、実フローを通したテスト

### 作らないもの

依頼書20章の全項目（日替わり景品、ログインボーナス、広告、課金、PayPay、
アカウント、ソーシャル、フレンド、トレード、ガチャ）。

加えて次も作らない。

- ぬいぐるみの命名（前フェーズで次点としたが、キャラクター育成に寄る危険がある）
- 親密度の数値表示（依頼書10章で明示的に禁止）
- 家具・小物
- 自律的な移動（ぬいぐるみが勝手に位置を変えることはしない）

## 3. 最重要の設計原則

依頼書30章より。実装中に迷ったらここに戻る。

> ぬいぐるみは静的な Collection Item ではなく、**ほんの少しだけ生きている存在**。
> ただし喋りすぎたり自律行動をしすぎたりして、キャラクター育成ゲームにはしない。
> 目標は「棚を眺めていると、ときどき『かわいいな』と思うこと」。

この原則から次の3つの実装判断が導かれる。

1. **棚での関係リアクションに吹き出しを使わない。** 動きだけで表す。
   12匹がしゃべり始めた時点でキャラクター育成ゲームになる。
   吹き出しはタップ時と出会いの演出にだけ残す。
2. **挿話的な演出は、棚全体で同時に1つだけ。**
   一斉に動くと「生きている」ではなく「騒がしい」になる。
   「眺めていたら偶然見つけた」感覚を守る。
3. **数値は一切出さない。** 関係は挙動だけで伝える。

## 4. Priority 1 — 個体と来歴

### 4.1 データモデル

`OwnedPlush` を `PlushInstance` に改名する。改名は機械的だが意味がある。
このフェーズの主張は「種類ではなく個体」であり、型の名前がそれを表明する。

```ts
type PlushOrigin = "starter" | "crane" | "granted";

type PlushInstance = {
  instanceId: string;
  plushTypeId: string;
  acquiredAt: number;              // epoch ms

  /** 何回目の試行で取れたか。null = 不明（v1 からの移行分、および starter） */
  attemptsToAcquire: number | null;
  /** そのとき見守っていた個体の instanceId。null = 不明 */
  witnessedBy: string | null;
  /** どうやって家に来たか */
  origin: PlushOrigin;

  /** 棚の水平位置 */
  x: number;
  /** 棚の段。-1 は箱の中 */
  shelfRow: number;

  personalitySeed: number;
};
```

**`origin` を明示的に持つ理由**: 「最初からここにいた子」と「来歴が不明な子」を
`attemptsToAcquire === null` から推測すると、v1 移行分と starter が区別できない。
プロフィールの文面が変わるので、推測ではなく記録する。

### 4.1.1 保存スキーマ v2

```ts
type SaveV2 = {
  version: 2;
  sessionCount: number;
  instances: PlushInstance[];        // v1 の owned
  craneBoard: CraneBoardSave | null;
  attempts: number;
  pendingWelcome: string | null;     // instanceId
  firstMeetingDone: boolean;
  /** 隣接ペアが隣同士になった時刻。キーは instanceId 2つの辞書順 "a|b" */
  neighborSince: Record<string, number>;
  log: LogEvent[];
};
```

`neighborSince` はリンクが切れたら削除する。所持上限が 12 匹なので
リンクは最大 20 前後にしかならず、無制限には育たない。

同じ Bear でも次はすべて別個体として保存する。スタックしない。

- 最初から家にいた Bear（`origin: "starter"`）
- 3回目で取った Bear（`attemptsToAcquire: 3`）
- Rabbit が見守っているときに取った Bear（`witnessedBy: <RabbitのinstanceId>`）

### 4.2 v1 → v2 移行

既存の保存データを**破棄しない**。棚が黙って消えるのは、このゲームの主旨に真っ向から反する。

| v1 | v2 |
|---|---|
| `uid` | `instanceId` |
| `defId` | `plushTypeId` |
| `seed` | `personalitySeed` |
| `acquiredAt` / `x` / `shelfRow` | そのまま |
| `owned` | `instances` |
| （なし） | `attemptsToAcquire: null` |
| （なし） | `witnessedBy: null` |
| （なし） | `origin`: 最古の1匹のみ `"starter"`、他は `"crane"` |
| （なし） | `neighborSince: {}` |

`version: 2` を書き、v1 を読めたら移行して即座に v2 として保存し直す。
`version` が 1 でも 2 でもない、あるいは移行に失敗した場合のみ初期状態に戻す。

### 4.3 取得時の試行回数を正しく保存

前フェーズのレポートで「試行回数は保存済み」と書いたが**事実誤認だった**。
今回は実際に保存する。

保存の要点は**捕まえるタイミング**にある。`attemptsOnBoard` は盤面ごとのカウンタで、
獲得して盤面が補充されると 0 に戻る。したがって

> **`won` イベントを処理する時点で、リセットが起きる前に読む。**

`store.winPlush()` の引数を変える。

```ts
winPlush(input: {
  plushTypeId: string;
  attemptsToAcquire: number;
  witnessedBy: string | null;
}): string
```

呼び出し側（`ArcadeScreen`）が `crane.attemptsOnBoard` と見守り個体の
`instanceId` を渡す。ストアが盤面の事情を知る必要はない。

### 4.4 検証（ここが最重要）

**数式や閾値だけを検証するテストを保証として扱わない**（依頼書23章）。
前フェーズで、解析テストは通っていたのに実際の獲得率が
想定 23.6% に対し実測 86.7% だった事故を繰り返さない。

`attemptsToAcquire` は次のテストで固定する。

1. クレーンと物理を実際に回し、N 回目の DROP で獲得する状況を作る
2. `store` に保存された `PlushInstance.attemptsToAcquire` が N であることを確認
3. N = 1, 2, 3, 4 のそれぞれで確認
4. 獲得後に盤面が補充されても、保存済みの値が書き換わらないことを確認

### 4.5 プロフィール表示

ぬいぐるみをタップすると、下から小さなカード（Bottom Sheet）が出る。
**大きなモーダルにしない。ステータス画面にしない。**

```
ミルクラビット

9月4日にやってきた
3回目でおうちに来た
ブラウンベアが一緒に見ていた

もりのおともだち
```

- 情報が無い行は出さない（`attemptsToAcquire === null` なら2行目を省く）
- `origin: "starter"` の場合は「はじめからここにいた」の1行だけ
- 数値・レアリティ・能力値は出さない
- 目的は**獲得体験そのものを思い出として保存すること**

### 4.6 タップの振る舞い

タップで**リアクションとプロフィールが同時に起きる**。

- その子がフニッと潰れて、こちらを見る（既存の挙動を保つ）
- 同時に下からプロフィールカードが出る

撫でたら反応する体験を消さない。「撫でたら反応して、この子のことを思い出した」
という一連の動作にする。

ドラッグ（4px 以上動いた場合）はタップではないので、どちらも起きない。

## 5. Priority 2 — 棚で持続する関係

### 5.1 隣接の定義

関係は**棚のどこに置かれているか**から生まれる。これによりプレイヤーが
並べ替えること自体に意味が生まれる（依頼書8章）。

棚は棚板に吸着するが、隣接判定は**2D距離**で行う。

```ts
shelfPointOf(p: PlushInstance) = { x: p.x, y: SHELF.rowY[p.shelfRow] }
NEIGHBOR_DISTANCE = 110
```

| 位置関係 | 距離 | 隣接 |
|---|---|---|
| 同じ段の隣（スロット間隔 82px） | 82 | ○ |
| 真上・真下（段間隔 102px） | 102 | ○ |
| 斜め | 131 | ✗ |

**斜めを外すのは意図的**。隣接が「真横か真上下」に限られると、
プレイヤーから見て**どう置けば隣になるかが読み取れる**。
斜めまで含めると、ほぼ全員が隣接して配置の意味が消える。

### 5.2 リンク

```ts
type NeighborLink = {
  a: string;                  // instanceId
  b: string;
  distance: number;
  /** 0-1。近いほど 1 */
  closeness: number;
  sameType: boolean;
  /** 一方が他方に見守られて家に来た */
  cameHomeTogether: boolean;
  /** 隣同士でいる時間 (ms) */
  togetherMs: number;
};
```

`togetherMs` は保存する。ペアのキー（`instanceId` の辞書順の組）をキーに
`neighborSince: Record<string, number>` を持ち、リンクが切れたら削除する。
所持上限が 12 匹なのでリンクは最大でも 20 前後にしかならない。

### 5.3 親密度（UIには一切出さない）

完全ランダムにすると配置の意味が薄れる（依頼書10章）。次の重みで決める。

```
affinity =
    closeness            * 1.0     // 距離が近い → 寄りかかりやすい
  + sameType             * 0.5     // 同じ種類 → 同期行動が起きやすい
  + cameHomeTogether     * 0.8     // 一緒に迎えた → 視線・寄りかかりが起きやすい
  + min(togetherMs/120s, 1) * 0.4  // 長く隣同士 → 軽い同期が増える
```

**この数値をUIに出すことを禁止する。** 「Affinity +3」の類は作らない。
関係は挙動だけで伝わること。

### 5.4 関係の演出 — 2層に分ける

#### 常時層（静かに、常に効いている）

- **Lean（寄りかかり）**: 隣の方へごく僅かに傾く。傾き = `affinity` に比例、最大 3.5 度
- **Breathing Sync（呼吸同期）**: 隣が近いほど呼吸の位相が引き寄せられる

この2つは前フェーズの終わりに素朴な形で入れたもの。親密度で強さを変える。

#### 挿話層（まれに、棚全体で同時に1つだけ）

| 種類 | 内容 |
|---|---|
| `look` | 片方が隣を見て、少し遅れてもう片方も見る |
| `sameDirection` | 2匹が同じ方向を見る |
| `sleepTogether` | 片方が眠そうになると、もう片方も少し眠そうになる |
| `greeting` | 新しく隣に置かれた直後の短い挨拶モーション |

**制約**

- 同時に走る挿話は**常に高々1つ**
- 次の挿話までの間隔は 6〜14 秒
- 対象のリンクは `affinity` で重み付けして選ぶ
- 1つの挿話は 2〜3 秒で終わる
- `greeting` だけは即時。新しいリンクができた瞬間に割り込む

「棚を見た瞬間に『生きている！』と強く思わせる」のではなく、
「なんかこの子たち、一緒にいるな」と感じる程度に留める（依頼書9章）。

### 5.5 同種ならではの挙動

同じ種類が複数いる場合も別個体だが、少しだけ特別な挙動を足す。

- 同種2匹: 呼吸が同期しやすい（`sameType` の重み）、`sameDirection` が起きやすい
- 同種3匹以上が互いに隣接: たまに全員が同じ方向を見る

**ゲーム的報酬にしない。** 「3匹集めるとボーナス！」は作らない。
プレイヤーが自然に「Bear だけ並べたい」と思えれば成功。

### 5.6 個体差

`personalitySeed` から導く。明確な能力差ではなく「なんとなく違う」程度に留める。

| 値 | 範囲 |
|---|---|
| `scale` | 0.96 〜 1.04 |
| `idleSpeed`（呼吸の速さ） | ±5% |
| `blinkInterval` | 3〜7 秒 |
| `leanPreference`（寄りかかりやすさ） | 0.7 〜 1.3 |
| `sleepiness`（眠りやすさ） | 0 〜 1 |
| `socialDistance`（隣との距離の好み） | 0.85 〜 1.15 |

**`socialDistance` は隣接判定の閾値には使わない。**
個体ごとに閾値が違うと、A から見て隣なのに B から見て隣ではない、という
非対称なリンクが生まれ、「どう置けば隣になるか」がプレイヤーから読み取れなくなる。
リンクの成立は全個体共通の `NEIGHBOR_DISTANCE` で決め、
`socialDistance` は**寄りかかりの強さ**にだけ効かせる（近寄りたがりの子は少し深く傾く）。

`sleepiness` は `sleepTogether` の挿話が選ばれる重みに効かせる。

前フェーズで、色相回転だけでは彩度の低い体色に効かないことが分かっている。
色は彩度・明度も併せてずらす（既存の実装を維持）。

### 5.7 配置 → 反応のフィードバック

配置変更のたびに隣接を再計算する（依頼書14章）。

```
Bear の隣に Rabbit を置く
  → リンクができる → greeting が即座に走る
  → しばらくすると寄りかかりが強くなる（togetherMs が伸びる）
Rabbit を離す
  → リンクが切れる → 傾きが 0 へ戻る
```

**離されたときも何も起きないのではなく、傾きがゆっくり戻る**ことで
「関係が解けた」ことが見える。前フェーズの積み残しへの回答。

### 5.8 Idle 時間の設計

棚を開いて何も操作しなくても、小さな出来事が起きる（依頼書15章）。
挿話層がそのまま Idle の仕掛けになる。

イベントを連発しないこと。**「眺めていたら偶然見つけた」感覚が重要**。
`shelf_idle_10s` / `shelf_idle_30s` をログに残し、実際に眺めていられたかを見る。

## 6. Priority 3 — 並べ替え

依頼書13章の6条件を全部満たす。

### 6.1 指で隠れない × 棚板から浮かない

この2つは一見矛盾するが、**足元を掴んで、ぬいぐるみを指の上に描く**ことで両立する。

- ドラッグ中、ぬいぐるみは指の位置ではなく**指の 46px 上**に描く
  （最大の景品の直径 72px の半分より少し大きく取り、顔が確実に見える）
- 縦位置は常に最寄りの棚板の上面ラインに吸着する
- したがって移動中も常にどこかの棚板に立っており、指はその下にある
- 掴んだ瞬間に飛び上がらないよう、オフセットは 120ms かけて付ける

### 6.2 置ける場所が分かる

ドラッグ中、着地予定の棚板に淡い楕円の影を出す。
置けない場所（定員オーバー）では影を出さない。

### 6.3 Drop 時に不自然なジャンプをしない

現在は `snapPlacement` の結果へ瞬間移動している。
ドラッグ位置から確定位置まで **180ms で滑らせる**。

### 6.4 距離感が自然

押し出しの最低間隔は「隣り合う2匹の半径の和」で決める（前フェーズで修正済み）。
加えて、隣接距離 110px の内側に収まる位置を優先して吸着させる。

## 7. Priority 4 — Reaction Director

### 7.1 目的

前フェーズの最重要の発見は、**落下時にプレイヤーが景品ではなく見守り
ぬいぐるみを見た**ことだった。この効果を強めるため、物理イベントを
感情反応へ変換する層を明示的に作る（依頼書16章）。

### 7.2 物理から拾うイベント

`step()` の返り値を拡張する。

```ts
type StepResult = {
  fallen: string[];
  impacts: number;
  /** このステップで起きた最大の衝突速度。驚きの判定に使う */
  maxImpactSpeed: number;
  /** 動いている景品の数。左右を見る判定に使う */
  movingCount: number;
};
```

### 7.3 イベントと反応

| イベント | 反応 |
|---|---|
| `won` | 大喜び |
| `almost_goal`（静止後、対象が出口 60px 以内） | 出口をじっと見る |
| `near_miss`（掴んだのに落とした） | 身を乗り出して「あっ！」 |
| `grab_success` | 期待 |
| `big_bounce`（`maxImpactSpeed` が閾値超え） | 驚く |
| `two_plushes_move`（`movingCount >= 2`） | 左右を見る |
| `weird_stuck`（`settle` の再試行を使い切った） | 首をかしげる |
| `idle` | ゆるい呼吸 |

### 7.4 優先順位

複数イベントが同時に起きた場合の優先順位（依頼書17章）。

```
WON > DROP_NEAR_GOAL > DROP > GRAB > BIG_MOVE > IDLE
```

各反応に**最低表示時間**を持たせ、その間は同順位以下のイベントで上書きしない。
吹き出しとアニメーションが重複しないことを保証する。

これを `directCrane(state, events, now)` という純粋関数に閉じ込め、
優先順位のテストを書く。

## 8. 吹き出しの配置

前フェーズで吹き出しがクマの顔を覆う問題があった。共有の配置関数に統一する。

```ts
placeBubble(opts: {
  anchorX: number;      // ぬいぐるみの中心
  headTopY: number;     // plushTop() の値
  textWidth: number;
  bounds: { minX: number; maxX: number; minY: number };
  others: { x: number; headTopY: number }[];  // 他の子の頭
}): { x: number; y: number; below: boolean }
```

保証すること。

- 自分の顔に被らない（頭上へ逃がす）
- 画面外に出ない（上端に近ければ下側へ回す）
- 他の子の顔に被らない（横へずらす）
- スマホ縦画面で読める大きさを保つ
- クレーン操作のボタンに被らない

## 9. プレイログ

追加するイベント（依頼書21章）。

```
plush_profile_opened
plush_drag_start
plush_drag_end
neighbor_created
neighbor_removed
relationship_reaction   // meta: { source, target, reactionType }
shelf_idle_10s
shelf_idle_30s
shelf_return_after_win
```

`buildLogJson` のサマリに、依頼書22章の A〜F を集計する。

| | 見たいこと | 集計 |
|---|---|---|
| A | 取得後、何秒棚を見ているか | `shelf_return_after_win` から次の離脱までの中央値 |
| B | 取得後、並べ替えるか | 獲得後 60 秒以内の `plush_drag_end` の数 |
| C | 既存の隣に新入りを置くか | 獲得後の `neighbor_created` の数 |
| D | 関係リアクション後に配置変更するか | `relationship_reaction` の 30 秒以内の `plush_drag_end` |
| E | 同じ種類を隣に置くか | `sameType` なリンクの数 |
| F | プロフィールを開くか | `plush_profile_opened` の数 |

## 10. テスト方針

### 10.1 原則

**数式や閾値だけを検証するテストを保証として扱わない**（依頼書23章）。
必ず実際のゲームフローを通したテストを入れる。

前フェーズの事故:

| | 想定 | 実測 |
|---|---|---|
| 1回目獲得率 | 23.6% | 86.7% |

解析テストは閾値の計算しか見ておらず、実際に `won` が出るかを見ていなかった。

### 10.2 クレーン E2E シミュレーション

`Drop → Grab → Physics → Drop/Win` まで実際に回す。
**最低 300 セッション**、次を測定して記録する。

- 1回目獲得率
- 2回目までの累積獲得率
- 3回目までの累積獲得率
- 4回目までの累積獲得率

意図した難易度から大きくずれていないことを確認する。
測定値はテストの出力に残し、レポートにも載せる。

### 10.3 来歴の保存

4.4 のとおり、実フローを通して `attemptsToAcquire` を検証する。

### 10.4 隣接と関係

- 隣接判定が距離のとおりに働く（同段の隣・真上下は隣接、斜めは非隣接）
- 配置変更でリンクが作られ、離すと消える
- 挿話が同時に2つ以上走らない
- 親密度が高いリンクほど選ばれやすい
- 12 匹全員が隣接しても破綻しない

### 10.5 Reaction Director

- 優先順位が守られる（低い順位のイベントが高い順位を上書きしない）
- 最低表示時間の間は同順位以下で上書きされない
- 吹き出しが同時に2つ出ない

## 11. 「4回以内保証」の表現

前フェーズのレビューで指摘されたとおり、この保証には限定条件がある。

> **同じ景品を継続して狙った場合**に限り、4回以内に獲得できる。
> 不変条件は「その試行の対象」に対して働くため、毎回別の景品を狙えば
> 1匹あたりの前進はその分ゆっくりになる。

この条件を**コードコメント・テスト・レポートのすべてに明記する**。
保証できないものを保証と書かない。

## 12. 取得判定

次の問題を再発させない（依頼書26章）。

- 空中にいる景品を床上移動として扱わない
- 摩擦適用前提の移動量を空中速度に使わない
- 狙っていない景品が偶然出口に押し込まれて謎の獲得にならない

**「何が原因で獲得になったか」がプレイヤーから見て理解可能であること**を重視する。
転がっていった景品が別の子を突き落とすのは、目で追えるので許す。
最後の手段の直接配置が別の子を押し込むのは、理由が見えないので禁止する。

## 14. 実装後の報告

コードレビューだけで終わらせない。必ず実際にプレイする（依頼書27章）。

必ず試すこと。

| | 内容 |
|---|---|
| A | 新しいぬいぐるみを取る |
| B | 棚へ戻る |
| C | 新入りを既存ぬいぐるみの隣に置く |
| D | 30秒間、何も操作せず棚を見る |
| E | 配置を変える |

そのうえで依頼書28章の8項目に答える。

1. Strongest Emotional Moment
2. Weakest Moment（ぬいぐるみが単なる UI オブジェクトに見えた瞬間）
3. Shelf Behavior（30秒眺めていられたか）
4. Rearrangement（配置を変えたくなったか、その理由）
5. Duplicate Test（同種2匹が「別々の2匹」に見えたか）
6. Provenance Test（来歴が愛着に影響したか）
7. Relationship Test（最も自然だった／人工的に見えた挙動）
8. Next Hypothesis（Retention 検証の準備ができているか）

## このプロジェクトの芯

見失いやすいので最初に書きます。

> クレーンは**入手方法**。棚は**生活する場所**。
> ぬいぐるみ同士の関係が**感情的報酬**。

プレイヤーが「この子を取った」ではなく「**この子がうちに来た**」、
さらに「**この子たち、一緒に暮らしてる**」と感じることを目指しています。

第1フェーズの実プレイで分かった最も重要なこと:

- 景品を落とした瞬間、**プレイヤーは景品ではなく見守りぬいぐるみを見た**
- 2匹が並ぶ嬉しさの中身は「並んだこと」ではなく、**先輩が振り向いて見たこと**だった

どちらも「モノが増えた」ではなく「関係が生まれた」ことによります。
第2フェーズはこの関係を棚でも持続させるのが目的です。

## 再開時に踏んでほしくない地雷

計画書に理由付きで書いてありますが、**一度間違えて直した箇所**なので念のため。

### 1. `Body.defId` と `CraneBoardSave.prizes[].defId` を改名しない

第2フェーズで `OwnedPlush.defId` → `PlushInstance.plushTypeId` に改名しますが、
**アーケード側の `defId` は別物**です。全域置換すると物理・盤面保存・`getPlush()` が
すべて壊れます。型名で絞って置換してください。

### 2. ID 文字列から種類を復元しない

`bodyId.split("#")[0]` で種類を取り出す設計は、ID の作り方を変えた瞬間に
**静かに壊れます**。物理が景品を取り除くときに種類も一緒に報告する形にします
（計画 Task 2）。

### 3. 隣接を距離だけで決めない

12匹を同じ場所に重ねると総当たりで66本のリンクが張られます。それは「隣にいる」
ではありません。左右上下でいちばん近い1匹だけとリンクします（計画 Task 4）。

### 4. 空中の物体に「床を転がる距離」の初速を与えない

第1フェーズで**掴み失敗が獲得に化けていた**原因です。摩擦は接地中しか効かないため、
30px のつもりが 130px 以上飛んでいました。`advanceImpulse` のコメントに
警告を書いてあります。

### 5. 「4回以内に取れる」は無条件の保証ではない

**同じ景品を継続して狙った場合**に限ります。不変条件は「その試行の対象」に
対して働くため、毎回別の景品を狙えば1匹あたりの前進は遅くなります。
コード・テスト・レポートのすべてにこの条件を併記してください。

### 6. Developer Menu の破壊的操作を1度押しに戻さない

公開先（GitHub Pages）にも Developer Menu は入っている。1回の誤タップで
「所持品リセット」「localStorage全消去」が走ると、プレイヤーが連れて帰った子が
全部消える。このゲームで最も起きてはならない事故なので、`DangerButton` で
2度押しにしてある。`src/dev/DevMenu.test.tsx` が固定している。

### 7. 起動時の最初の隣接パスで created を報告しない（ただし迎えた子は例外）

過去の関係を「今できた」と報告すると、**アプリを開くたびに全員が挨拶し直す**。
一方で、クレーンで取った子は必ず既存の子の隣に置かれるので、その1本だけは
本物の新しい関係。演出中は隣接計算が止まるため、素直に書くと
「演出後の最初のパス＝復元」と誤判定して**獲得直後の挨拶が丸ごと消える**。
`arrivedGuestRef` で迎えた子を捕まえて例外にしてある。
`src/shelf/ShelfScreen.test.tsx` が固定している。

### 8. computeNeighbors に created を渡しっぱなしにしない

`tickDirector` は「実行中の挨拶」の再開始しか抑止しない。自然終了した瞬間に
古い `created` がまた挨拶を始めるため、**同じペアが2〜3秒ごとに永遠に挨拶する**。
渡したら消すこと。`useAmbientLife.stepRelations` が無条件に消している。

### 9. episodePose ではなく directorPose を呼ぶ

`episodePose` は実行中の挿話しか見ないので、300ms のフェード状態が抜ける。
直接呼ぶとフェードが消えてスナップに戻る。返る `NEUTRAL` は `Object.freeze`
してあるので、その場加算（`p.tilt += lean`）は例外で落ちる。落ちるのが正しい。

### 10. window のイベント購読を、毎レンダー変わる値に依存する useEffect に置かない

第2フェーズでドラッグが完全に壊れていた原因。`onTap` を deps に入れていたため、
`ShelfScreen` が毎レンダー渡す新しいクロージャで再購読が走り、クリーンアップが
`pointerIdRef` を null にしていた。結果、2回目以降の `pointermove` が捨てられ、
`pointerup` が commit されず、**`plush_drag_end` が一度も記録されていなかった**
（指標Dが成立していなかった）。いまは `pointerdown` の中で命令的に購読している。

### 11. `NEIGHBOR_LINK_DISTANCE` を `neighbors.ts` に戻さない

定義は **`shelfLayout.ts`** にあり、`neighbors.ts` は再エクスポートしているだけ。
配置側（`snapPlacement` の仕様6.4「隣になれる位置を優先する」）と関係側が
同じ 110 を見る必要があるが、`neighbors.ts` は `SHELF` を使うので、
配置側がそちらから借りると循環参照になる。両方に 110 と書き写すのは
もっと悪い（「隣に置いたつもりが隣にならない」形で静かに壊れる）。

### 12. ドラッグ中の描画 y に持ち上げのランプを掛けない

`poseOf` の 120ms のランプは**段を選ぶ基準にだけ**掛ける。描く y は常に
`rowY(row)`。ここに `e` を掛けて補間すると、掴んだ直後の 120ms だけ
足元が段と段の間に浮き、同じフレームで着地の影（必ず段の上面ラインに出る）と
胴体が別の高さになる。仕様6.1 の「常に棚板の上面ラインに吸着」はランプ中も含む。
`tick(200)` してから調べるテストではこの帯を素通ししてしまうので、
ランプの途中を 8ms 刻みで見るテストを足してある。

## テストについての教訓

第1フェーズで、解析テストは通っていたのに実際の獲得率が
**想定 23.6% に対し実測 86.7%** でした。

> **数式や閾値だけを検証するテストを保証として扱わない。**
> 必ず実際のゲームフローを通したテストを入れる。

同じ理由で、次のテストは書いても意味がありません。

- `store.winPlush({attemptsToAcquire: 3})` を呼んで 3 が保存されることを確かめる
  → 「渡した値が保存される」ことしか言っていない
- `requiredHold(n) === RELEASE_THRESHOLD + drain(n)` を確かめる
  → 実装の写経

代わりに、実物の物理と状態機械を回して結果を見てください。

## 開発中に知っておくと楽なこと

### ブラウザでの動作確認

ブラウザペインが非表示のときは `requestAnimationFrame` が止まります
（アプリ側の `visibilitychange` ハンドラで意図的に止めている）。
そのため JS で待っても物理が進みません。**スクリーンショットを撮ると1フレーム進みます。**
連続で確認したいときはスクリーンショットを並べてください。

### Vite の変換キャッシュ

エクスポート名を変えたのに `ReferenceError: XXX is not defined` が出る場合、
HMR が古いモジュールを掴んでいます。

```bash
rm -rf node_modules/.vite
```

でキャッシュを消して dev サーバーを再起動してください。

### Developer Menu

棚画面の**右下の小さなドットを3回タップ**、または `Ctrl + Shift + D`。
所持品リセット、任意のぬいぐるみ追加、プレイログの JSON ダウンロードができます。
